# Commit, Push, and Deploy Workflow

For every task that changes a Git worktree:

1. Work in coherent, reviewable checkpoints. Group related edits that share one purpose; do not create a checkpoint after every small edit, and do not bundle independent features, fixes, refactors, or documentation changes into one bulk commit.
2. At each checkpoint, select the smallest validation set that covers the changed paths, affected contracts, and realistic risk. Prefer focused unit, lint, type, build, render, or smoke checks before broader suites. Run canonical CI when repository policy requires it, and use broader integration or end-to-end coverage for cross-cutting behavior, shared infrastructure, migrations, security boundaries, production data paths, or evidence of wider impact. Commit only after the selected checks pass, or clearly report any known failure or blocker.
   - Reuse passing evidence when the candidate bytes, dependencies, configuration, platform and tested contract are unchanged. A handoff, review, resumed turn, repaired receipt or status request does not by itself justify rerunning a workload. After an observer-only repair, rerun only the affected observer or assertion. Expand coverage when an input changed, the previous environment is no longer representative, a failure suggests collateral impact, or a required gate has not run.
   - The specialized cases below are conditional references, not a checklist for every checkpoint. Apply a case only when its trigger is present. Keep one authoritative evidence set for the candidate and reference its retained logs and receipts; do not duplicate unchanged captures, builds, test outputs or backups. Preserve original failures and create or refresh recovery assets only before destructive or difficult-to-reverse steps when existing rollback coverage is missing or stale.
   - Distinguish direct dependency discovery from complete released-tree coverage. Inspect tracked overrides/resolutions and installed transitive inventories; a clean top-level outdated result does not establish that every pinned package is current. Preserve upstream dependency constraints unless a separately reviewed override is justified.
   - Validate nested tool workspaces with their own declared dependencies and a clean parent directory. A root `node_modules` can supply undeclared type packages and conceal a standalone CI failure. Include required generated inputs, keep build output out of source type checking, and install at the final validation path before testing the isolated workspace.
   - If a high-core workstation test run times out under worker contention, preserve the failing timings and rerun with a bounded worker pool before changing deadlines, assertions, or source. Record that execution limit and still run the repository's exact canonical CI on its intended platform before production promotion.
   - Before parallelizing builders and type checks, inspect their generated output paths. Commands that write the same component, route or other declaration file are dependent even when their final bundles have different output directories. Serialize those producers before the consuming type check, or use separate installed checkouts. Preserve any original race failure and generated diff; once every writer is terminal, restore only verified agent-generated leaves and validate the exact publication snapshot. Do not absorb generated path-prefix noise or weaken type assertions to hide concurrent writes.
3. Review the staged diff. Include only work in scope, and never commit unrelated user changes, generated noise, captures, credentials, or secrets.
   - For read-only three-way file analysis, use `git merge-file --stdout` and retain stdout, stderr and the exit status before classifying the result. Its documented nonnegative exit value counts conflicts, capped at 127; more than one conflict is not a tool failure. Keep conflict-bearing output separate from a qualified merge, and resolve and test the combined source before publication. See the [git-merge-file contract](https://git-scm.com/docs/git-merge-file).
   - When selective staging produces a source snapshot different from the tested worktree, export the exact index into a fresh temporary directory and run the relevant build/tests there too. A dirty worktree can supply missing methods, visibility changes, or request parameters that conceal a broken staged commit. Resolve required dependencies explicitly without absorbing unrelated prototype changes, and distinguish staged-snapshot results from worktree/device results in the handoff.
     A file clean against an older local HEAD is not necessarily aligned with the intended publication base. Before transplanting whole owned files from a deliberately preserved behind checkout, compare each file with that exact base and carry forward its intervening changes. Prefer applying the narrowly reviewed task patch to the current baseline. Check additions and deletions inside every selected file, preserve existing regression controls, and qualify that exact snapshot; a changed-path allowlist and passing build alone cannot detect an accidental rollback within an allowed file. Preserve a rejected snapshot separately without resetting the dirty checkout or repeating completed device work.
     Before staging newly created files, `git diff <proposed-tree>` is not a complete worktree-content check: it can report those paths as deleted because they are absent from the current index even while their untracked files exist. Verify each explicit owned file against the proposed blob with repository clean filters, stage only those paths, and then compare the selected index. Preserve an earlier refusal without misclassifying it as changed source or repeating a completed workload.
   - GitHub source tarballs and `git archive` can omit tracked files through `.gitattributes` `export-ignore` or alter them through `export-subst`. Before treating an archive as the exact source commit, reconcile its contents against that commit's Git tree and blob hashes, including workflow, build-context and contribution files. Preserve executable and symlink semantics on the intended platform; a Windows pointer-file checkout does not verify a Linux packaging symlink.
     An exported source directory nested beneath another Git repository can inherit that ancestor's history and break Git-dependent validation. Give the snapshot its own temporary Git metadata, bind its HEAD/history to the intended baseline and its index to the candidate tree, then verify `git rev-parse --show-toplevel` and required path history before tests. Write Git metadata such as `objects/info/alternates` as explicit UTF-8/LF bytes; Windows CRLF translation can become part of the alternate object path. After a metadata repair, retain the original failure and rerun only the affected check and still-unexecuted work against unchanged source bytes.
     On Windows, `git archive` can also apply `core.autocrlf` even without a tracked `.gitattributes`, producing CRLF text that differs from the raw blobs. For an exact-byte snapshot, export with the per-command override `git -c core.autocrlf=false archive ...`, without changing shared Git settings, then verify every extracted file against its raw blob before building. Preserve a mismatched export and its results; do not relax the byte guard or silently normalize it after validation.
     Compare deployed Linux source and descriptor bytes with the selected publication tree's raw Git blobs, not a Windows working-copy hash. Checkout line-ending conversion can make unchanged JSON appear to drift. Preserve the original comparison refusal, verify the exact blob/path inventory offline, and repair only the observer rather than syncing, rewriting, or restarting a healthy service to satisfy a platform-dependent hash.
     TypeScript can also preserve checkout CRLF inside emitted multiline template literals. If a Windows-built artifact differs from a Linux deployment, retain that failure and diagnose the exact byte differences, then build a verification witness from a hash-verified LF/raw-blob export of the same published tree and locked dependencies. Require exact installed-byte parity against that witness; do not normalize the deployed files, relax the final hash guard, replay passing health checks, or redeploy completed work merely to repair a platform-dependent artifact comparison.
     Derive compiled witness paths from the actual compiler configuration, copy/minification steps and emitted manifest, then require every selected path to exist before hashing. Source directory names alone do not establish emitted runtime paths. When adapting a previously repaired helper, carry its corrected observer and path inventory forward as well as its successful build. Preserve a stale-path refusal and reuse the unchanged qualified output; do not repeat the build or promotion merely to finish a receipt.
     Keep that archive-only override out of `git add`: disabling clean filters while staging mixed/CRLF text can turn a small edit into a whole-file line-ending change. If an incorrect staging invocation has already admitted those bytes, ordinary restaging can preserve them because Git sees CRLF in the index. Inspect `git ls-files --eol` and the exact staged diff, then use `git add --renormalize -- <explicit-owned-paths>` with the repository's intended clean filters. Recheck the staged whitespace/content and export/test the corrected tree; never broadly renormalize unrelated files or rewrite the working copy merely to conceal the failed index.
   - Run `git bundle verify` in an existing repository context, for example `git -C /path/to/repo bundle verify /absolute/source.bundle`; verification from a generic worker directory fails with "need a repository". Bind the transferred bundle hash, selected commit and checked-out blob contents independently, and keep repository credentials off the target when using a verified bundle for private-source delivery.
   - When converting a Git diff to another edit-tool patch format, validate its actual direction and both exact allowlisted paths before any write. `git diff -R` can display `b/path` before `a/path`; do not assume forward `a/path` then `b/path` headers. Test reverse, forward, mismatched and out-of-scope headers, and preserve a preflight refusal separately from a completed mutation.
   - When removing a feature with an automated source transformation, inspect complete conditions, shared callers and ownership before deleting a node. A condition containing the retired feature can also guard retained behavior; remove only that branch or operand, preserve shared invalidation and lifecycle hooks, and review the surviving control flow before testing. Limit every transformation and cleanup pass to an explicit owned-path allowlist; a live dirty-file inventory can include another task's concurrent changes.
   - When editing CSS or JavaScript stored in source templates, locate the exact named initializer with the language parser. A nearby export or the nearest backtick does not identify the intended template. Validate the actual emitted stylesheet and script, and compare script bytes when they should stay unchanged: TypeScript can compile a string containing malformed JavaScript. Preserve an invalid producer and rerun the corrected affected contract before accepting its output.
   - Before generating a PR or changelog from a named base, verify that the exact local ref resolved by the generator matches the current remote base and that `base..HEAD` contains only the intended commits. A targeted fetch by commit ID can leave `origin/<base>` unchanged after an upstream history rewrite. Reconcile only that remote-tracking ref with an expected-old-value update after verifying the remote SHA; preserve local branches, unrelated refs and candidate bytes. Retain and reject an earlier overbroad generated body, then regenerate without repeating passing application checks or publishing the rejected description.
4. Follow the repository's commit-message rules. When no stricter local rule exists, begin the imperative subject with `[feat]`, `[fix]`, `[perf]`, `[refactor]`, `[docs]`, `[test]`, `[build]`, `[ci]`, `[chore]`, or `[revert]`.
   - Qualify the actual commit graph consumed by release-note and updater generators. A blanket `--no-merges` filter can omit user-visible implementation introduced in a valid merge. Include required merge commits under the same type-prefix validation as ordinary commits, and test a real branched Git fixture whose merge contains a unique release entry. Verify multi-record parsing as well as note content. Compare the published notes and updater metadata with the tested source; retain immutable earlier releases and correct the next candidate instead of moving tags or claiming published notes from commit messages alone.
     In pull-request CI, GitHub can check out a synthetic merge whose untyped subject is not part of the published source history. Bind strict release-note validation to the immutable PR head SHA through an environment variable, while keeping application checks on the intended checkout. For push events, use the pushed SHA. Preserve real merge commits and strict type validation; do not add a blanket merge exclusion or allow-untyped bypass to accommodate the synthetic commit. Retain the original refusal and rerun only the repaired observer and application phases that it prevented.
   - Inspect active commit-lint workflows and their referenced configuration before choosing a subject; the absence of a contribution guide does not imply the cookbook default applies. A repository enforcing Conventional Commits requires its accepted `type(scope): subject` syntax. If a message-only correction is necessary after publication, preserve the original CI rejection, verify the Git tree stays identical, sign the amended commit and use an exact old-head lease for the affected branch; let canonical CI evaluate the new head.
5. In PowerShell, do not embed `\n` escape text inside a quoted `git commit -m` argument; PowerShell passes it literally. Supply each paragraph with a separate `-m` argument, or use a UTF-8 message file with `git commit -F`, so the recorded message contains real line breaks.
6. When repository policy permits intentionally skipping CI, put `[skip ci]` immediately after the normal tag, for example: `[docs][skip ci] Clarify deployment steps`. Never append it at the end.
   - Repository exception: never use `[skip ci]` in `bozo-industries/agent-cookbook`; use only the normal commit-type tag.
7. Push every completed, tested checkpoint to its configured remote. Do not leave finished work only in the local worktree unless pushing is technically blocked or a higher-priority instruction forbids it; report the exact blocker.
   - Before creating an integration branch locally, check for ref namespace conflicts: an existing `dev/topic` branch prevents a branch named `dev`. Preserve unrelated refs and worktrees; validate the explicit remote integration ref and use a detached checkout at the tested commit when only verification or completed feature-branch deletion remains.
   - Creating a new branch from a remote base can automatically give it that base branch as its upstream. Use `git switch --no-track -c <new-branch> <base>` when the new branch should publish under its own name, then verify its tracking target before any push. If only this newly created, unpushed branch inherited the wrong base upstream, remove that branch-owned tracking association and publish its explicit new ref; preserve existing user branch tracking and never let a routine push advance the base branch accidentally.
   - A repository-configured credential username can prevent an otherwise authenticated GitHub CLI helper from supplying credentials. After a Git authentication refusal, compare the configured username with the current authenticated API principal before requesting a new sign-in. When they differ, use command-local username and credential-helper overrides for the intended account, and verify a read-only remote operation before pushing. Preserve shared credential settings and keep authentication separate from the commit's required author, committer and signing metadata; never print helper responses containing tokens.
    After an account rename, the CLI can retain its active credential profile under the old login while the API returns the new login. Bind the profile to the live principal by stable account ID using non-secret metadata. If its helper selects credentials by the stored profile name, use that alias in the command-local override and qualify read-only remote access before pushing; do not rewrite shared authentication or print a helper token.
   - Before publication, verify the recorded author and committer against the repository's authorized attribution and check any required signature. A configured identity or a valid signature alone does not prove those metadata fields are correct. Repository-local user settings can override global defaults; use an explicit per-command identity when policy requires it without changing unrelated global settings.
    Verify the host's qualification of the new signed commit; an older cached verified commit does not qualify a later one after an account change. For a rejection, bind the actual signature issuer fingerprint/subkey, raw registered public-key UID and exact committer payload before attributing the reason. Keep local cryptographic validity separate from host email qualification, and do not infer a verified noreply address from an account name/ID or treat an unavailable metadata endpoint as an empty result. Account/key registration or private identity changes require their own authority.
    A hosting service's native PR rebase can create a new unsigned commit even when the original proposal was signed. Before using such a rebase under a signature gate, inspect its documented signing behavior; prefer the proposing bot's supported rebase or recreation path when its signature must be preserved. Verify the actual new commit's author, committer and host signature before approval or merge. Preserve an unsigned result and its passing evidence; recover through a signed bot proposal or a separately signed agent checkpoint with canonical checks for its new head. Never weaken the signature gate or treat a successful rebase command as proof of a verified commit.

   - After a Git host acknowledges an exact ref update, dependent PR merge metadata may still be stale. Retain the acknowledged ref/commit SHA and first read, then reconcile that same ref, commit, and PR through bounded read-only requests. Do not create another merge or repeat a ref write merely because an immediate PR view still says open. Treat source integration and hosted status confirmation as separate observations.
   - A bare `git clone --mirror` sets `remote.origin.mirror=true`, which conflicts with an explicit refspec push. For a targeted update, disable mirror mode for that invocation (`git -c remote.origin.mirror=false push ...`), specify the exact refspec, and use `--force-with-lease` for an intentional history rewrite. Use `--mirror` only when every remote ref is explicitly in scope.
8. Deploy only after the tested commit has been pushed. If deployment is requested or is an established required step, deploy and verify it. If deployment intent is uncertain, ask before deploying. That uncertainty does not block committing and pushing.
   - Source or manifest synchronization can trigger a process-worker reload before its compiled output is promoted. A warm daemon restart may then reattach that worker with the previous code still loaded. Treat source sync, compiled promotion, and worker activation as separate milestones: verify promotion, reload or restart only changed workers, then run freshness and health checks against those instances. If final verification fails, reconcile the installed revision, retained backup, worker identities, and completed steps before resuming activation or verification; do not repeat an already-applied deployment merely to repair its observer.
     An endpoint named reload may only reconcile configuration and legitimately return success with every worker unchanged. Trace the selected handler and retain its changed/unchanged result before choosing activation. Verify the existing PID/start identity and in-flight operation separately; use the supported process-restart operation when new compiled code must be loaded. A timeout waiting for an unpromised PID change is an observer failure, not proof of a failed or pending restart. Preserve that refusal and resume only the genuinely unexecuted activation.
     A module-only promotion does not imply module-only source synchronization. Before applying an advancing checkout, compare every enabled module's synchronized descriptors and runtime metadata with its installed compiled revision. New metadata can restart an unrelated old worker before that module's own deployment. Defer the apply until its owning workflow has coherently activated those changes, or use an established truly module-scoped synchronization path. Do not broaden promotion authority to hide the mismatch; retain any collateral failure and verify the affected service separately after its authorized recovery.
   - When a supervisor also fingerprints code and automatically reconciles workers, inspect that behavior before choosing activation. A direct process restart can leave the loader's remembered code fingerprint unchanged and trigger a second automatic replacement. Prefer the established scoped reconciliation path when it owns that fingerprint. Bind acceptance to the settled PID/start identity and its lifecycle record; reconcile unexpected replacements without repeating a successful build or promotion.
9. Report the commit hash, pushed branch and remote, tests run, and deployment status. Never claim deployment based only on a local test or successful push.
10. In an allowlisted repository, verify that a new portable guide or asset is included by the intended ignore rules before staging references to it. A failed multi-path `git add` can still leave some requested paths staged; stop the checkpoint on that failure and inspect the exact index. Confirm every newly referenced file is present in the staged snapshot before committing and publishing the reference. Add only the specific portable path to the allowlist; never broadly unignore runtime or machine-local state.
    When restaging an explicit file list, retain already-staged deletions without passing their absent, untracked paths to `git add` again. Reconcile the current index and worktree first; stage only paths that still exist or remain tracked, then verify the final staged diff and exported tree. Text-edit scripts must also avoid writing unchanged files: compare the intended text before saving, preserve existing line endings, and recover only known agent-created formatting changes if a bulk rewrite touched unrelated files.

11. Scope Java formatting with the formatter's supported line ranges or complete changed structural blocks. Do not reconstruct formatting by transplanting whitespace between token matches: unchanged tokens can cross a changed control-flow boundary and produce misleading indentation. Run Android lint after partial formatting as well as compilation; syntactically valid Java can still fail `SuspiciousIndentation`.
